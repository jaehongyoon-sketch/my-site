# Day 17 — durable trade-event collection and idempotent history processing

`/practice/events` provides account-owned order acceptance, buy fills, released buy reservations, sell reservations and sell releases. It shows recorded/processed timestamps, quantities, durable references, backlog counts and independent 25-row pages. “Processed” explicitly refers to history projection, not trade execution. Equal occurrence timestamps use a stable ID order, not a claimed execution sequence.

Committed trading tables remain authoritative. A bounded collector derives events from saved orders, match entries, cash release entries and sell reservation records. IDs are deterministic by source and event kind; a unique source constraint additionally prevents duplicates. It copies no counterpart identities and accepts no client event payload. Existing history before this release is eligible for collection. There is no timestamp watermark, so delayed facts and old timestamps are not skipped.

Sync is request-driven: the page's Sync/Process next batch button runs authenticated `POST /api/practice/events` with exactly `{action:'sync'}`. A request stages at most 100 missing events in one transaction, then processes at most 50 in another durable phase. `practice_trade_receipts` is the activity-v1 handler's projection/receipt, with one row per event. Receipt creation is atomic and repeatable; it does not reapply accounting or matching. If collection fails, its batch rolls back and sources remain discoverable. If processing fails, committed staged events remain pending and are retried on the next sync. There is no scheduler, cloud queue, continuous background worker, email, push notification, payment webhook or financial event replay in this release.

GET reads history, all-record backlog counts and the requested page in one snapshot. Account identity comes from the verified session; active-profile checks protect both reading and processing. A trading-restricted active user can still process/view their history. Suspended/closed accounts cannot. POST requires same-origin JSON, a bounded body and strict input. Both routes are private/no-store. No migration seeds or mutates customer trades or balances; 0012 creates empty event/receipt tables and indexes only.

Tests (159 total) cover all five kinds, partial-release quantity, expiry, concurrency/retry, preserved receipt timestamps, transaction failure, processor restart, >100 records, pagination without overlap, old timestamps, account isolation, strict payloads, suspended users and unchanged funds/fills/holdings. Disposable local HTTP accounts verify protected routes, cross-origin rejection, restricted-account read processing, owned events, idempotency and page rendering. Test fixtures are removed locally; no production test events are created.

Next: Day 18 deeper ledger/position/fill reconciliation. This history projection is infrastructure for later consumers; new financial or external consumers require their own atomic accounting and durable idempotency contracts. Real funding, verification, sell execution and settlement remain disconnected.
