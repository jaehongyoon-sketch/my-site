# 제휴사 추가와 실거래 전환

## 현재 구조

- app/page.tsx: 서버에서 MarketDataProvider를 통해 초기 시장을 읽음.
- app/market-app.tsx: UI. API 비밀키나 실거래 SDK를 포함하지 않음.
- lib/domain: 거래소에 종속되지 않은 시장·견적·상태 타입, 정수 센트 계산.
- lib/providers/contract.ts: 조회/비실행 견적만 허용하는 서버 연결 규격.
- lib/providers/demo.ts: fixture 데이터를 공급. 실제 거래소를 흉내 낸 체결 기록은 생성하지 않음.
- app/api/quotes: 입력 검증 후 서버에서 비실행 견적 생성. feeCents=null은 수수료 미확정이지 무료가 아님.
- app/api/orders: 항상 503. 환경변수 하나로 실거래가 켜지는 경로 없음.

## 제휴 전에 확인할 항목

1. 일반 개인 API 이용이 아니라 다수 고객을 위한 앱 제공·주문 전달이 계약상 허용되는가?
2. 우리 역할은 ISV, 소개업자, 중개업자 중 무엇인가? 필요한 등록·감시 책임은 누가 맡는가?
3. 앱 사용자와 거래 계정 연결 방식, 고객 동의, 접근 철회, 토큰 보관 방법은 무엇인가?
4. 본인 확인·거래 자격·주별/상품별 제한을 어떤 시스템이 결정하는가?
5. 자금 보관 기관, 입출금 API/호스팅 화면, 반환·분쟁·출금 제한은 어떻게 처리하는가?
6. 시세 표시·캐시·재배포 권리, 기본/최소 요금, 계약 해지·데이터 보관 조건은?
7. 주문 고유번호 조회, 재전송, 취소/체결 경합, 이벤트 재생, 장애 대응 기능은?
8. 최소 가격 단위, 소수 계약, 수수료 반올림, 시장 유형, 결과 정산·정정 방식은?
9. 수익 배분·거래 수수료·구독 등 허용되는 수익 모델과 사용자 고지 조건은?
10. 실거래 인증 테스트, 승인 기준, 지원 연락 체계와 운영 책임은?

## 새로운 연결부 구현 순서

1. 승인된 문서 버전과 권한을 기록한다. 공개 문서만으로 미공개 API를 추정하지 않는다.
2. 서버 전용 어댑터 파일을 추가하고 외부 응답을 내부 타입으로 검증·변환한다.
3. providerId + externalId로 상품을 식별한다. 다른 거래소의 같은 질문도 자동으로 동일 상품 취급하지 않는다.
4. 최소 가격 단위가 1센트보다 작으면 금액 스케일을 명시적으로 확장한다. 현재 1센트 타입에 반올림해 끼워 넣지 않는다.
5. 인증, 사용자별 인가, CSRF, 속도 제한, 승인·권한 상태를 서버에서 검증한다.
6. 별도 ExecutionProvider를 설계하고 주문번호·idempotency·상태 불명 복구를 구현한다.
7. 파트너의 계정/체결/잔액이 원본이다. 로컬 데이터는 대조 가능한 복제/감사 기록으로 관리한다.
8. 테스트 환경에서 중복·부분 체결·취소·이벤트 지연·재시작·출금 실패를 검증한다.
9. 파트너 인증·사업 승인·운영 준비가 완료된 환경에서만 실거래 라우트를 구현·활성화한다.

## 상업 출시 경계

- 거래소 제휴만으로 등록 의무 면제를 가정하지 않는다.
- 수익은 보장되지 않는다. 파트너 비용·데이터 비용·지원 비용과 수익 배분을 확인한다.
- 1일차에는 결제/구독 SDK와 거래 수수료 부과를 추가하지 않는다. 허용된 모델 확정 후 구현한다.
- 제품명 Event는 임시 이름이다. 상표와 도메인을 출시 전 확인한다.
- 개발용 배포와 실거래 운영 환경을 별도로 유지한다. 현재 Sites 배포는 비공개 개발 미리보기다.
